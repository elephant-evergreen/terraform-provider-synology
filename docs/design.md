# Design and dependencies

The provider communicates directly with DSM over verified HTTPS. Terraform owns ordering, state, import, and planning. The provider owns typed configuration, DSM API adaptation, readback, identity, cancellation, redaction, and safe failure behavior. There is no remote agent, custom CLI, shell transport, or generic API resource.

Existing named objects are adopted through import, never a create operation. Service singletons and complete local share-permission policies are configuration resources: Create applies declared settings, import adopts unchanged, and Delete only releases management. Read and discovery must reflect DSM rather than echo the previous Terraform state. A failed read does not establish absence. Unreadable secrets use write-only inputs and explicit generations; they are not presented as drift-detectable.

The user-home service requires import before any mutation. Its asynchronous operation baseline must survive failure and replacement; a stateless Create cannot recover an earlier pending target safely. Terraform import blocks support adoption and an intentional Update in the same plan. Targets and acknowledged task identities are returned in private state, existing DSM tasks are discovered before writing, and refresh only polls and reads. An unacknowledged operation returned to Terraform requires explicit reconciliation. A callback cannot durably commit state before its RPC returns. Process termination or loss of that RPC response can therefore lose the pending record. Exactly-once execution is not promised: after any interrupted apply, inspect DSM tasks and settings before planning again. Before writing, the adapter checks for running tasks and re-reads the current policy; an already-converged policy is not resent. The resource only sets convergent home-service policy and rejects relocation; it never retries a failed HTTP mutation. Existing home-folder relocation remains a separate data migration and is rejected by this resource.

Shared folders, built-in accounts, and management access have independent protection boundaries. Changes must preserve data, unknown API fields and settings outside the resource's schema. One share-permission resource owns every explicit local-user and local-group permission for its shared folder. Do not combine it with another ACL writer. Omitted principals inherit; they are not denied. Numeric UID/GID and share UUID bindings reject same-name replacements. File ACLs and domain principals remain outside this policy. Configuration backup is not a backup of user files. DSM does not offer a demonstrated transaction spanning these APIs; the provider cannot promise cross-resource atomicity or automatic restoration of data.

Initial compatibility work targets DSM 7.1.1 on DS220j. No hardware or lifecycle compatibility is claimed until the corresponding evidence is recorded. Storage pools, RAID, volume recreation, user-file contents, firmware installation, and execution of backups remain outside configuration lifecycle management.

## Dependencies

Go, pinned in go.mod and mise.toml, provides the standard HTTP, TLS, JSON and URL implementations for transport and parsing. HashiCorp's Plugin Framework v1.19.0, Plugin Go v0.31.0 and Plugin Testing v1.16.0 provide the official Terraform protocol, schemas and acceptance harness. gRPC v1.83.2 retains the router provider's vulnerability fix until the Framework selects a fixed version itself. golang.org/x/net v0.61.0 includes fixes for the reachable HTTP/2 advisories detected in v0.58.0. Go module checksums and vulnerability checks are required before release. The official Go govulncheck v1.9.0 is a build-time check; Google go-licenses v2.0.1 generates third-party license files. Neither is part of the runtime. They run without NAS credentials; their versions and module checksums are pinned by Go modules. Renovate and the existing checks own updates.

The existing synology-community/synology v0.6.11 implementation does not provide the required share and account resources and contains incomplete import and refresh behavior. batonogov/synology-dsm v0.8.1 provides useful API research, but targets newer DSM versions and does not establish the required lifecycle and safety guarantees for this deployment. A narrow, original typed adapter avoids adopting either provider's transport and resource semantics. This also makes DSM compatibility and maintenance the responsibility of this project.

References: [Synology File Station API](https://global.download.synology.com/download/Document/Software/DeveloperGuide/Package/FileStation/All/enu/Synology_File_Station_API_Guide.pdf), [HashiCorp resource design](https://developer.hashicorp.com/terraform/plugin/best-practices/hashicorp-provider-design-principles), [resource import](https://developer.hashicorp.com/terraform/plugin/framework/resources/import), [write-only arguments](https://developer.hashicorp.com/terraform/plugin/framework/resources/write-only-arguments), [API research at v0.8.1](https://github.com/batonogov/terraform-provider-synology-dsm/tree/v0.8.1/internal/client).

## Concurrent changes and interrupted creation

DSM does not provide an established atomic compare-and-swap contract. The provider serializes its own writes and checks object identities and complete prior permission policies immediately before writing. Another DSM administrator can still race after that check. Use one configuration writer, re-plan after changes, and inspect DSM after any failed apply. User and group policy updates can finish separately; no automatic rollback is promised.

A definite API rejection never adopts a same-name object returned by a later read. An unacknowledged create retains a provisional state and blocks refresh, update and delete until explicit reconciliation. Back up state, inspect DSM, remove only the provisional state entry, and import the confirmed object. Do not delete NAS data to repair state. An acknowledged create without confirmed UUID/UID/GID also blocks automatic refresh until explicit import reconciles ownership. Once a stable identity is confirmed, later membership failures retain that identity. Terraform can mark a failed creation tainted. After confirming ownership, use `terraform untaint` before reviewing another plan, rather than accepting replacement.

Authentication sessions and Synology tokens live only in process memory. The Framework has no guaranteed provider teardown hook; an abrupt Terraform exit can leave a DSM session until its server-side expiry. The production provider does not guarantee logout. Keep DSM session expiry and account privileges appropriate; read-only test probes explicitly log out.

A confirmed password update checkpoints its generation before later membership or readback operations. Re-running an interrupted apply does not resend an acknowledged rotation merely because a later step failed. Declare dependencies on all managed account resources for each complete share policy so Terraform schedules account creation before permission snapshots.

Terminal and rsync resources own their listening ports as well as service flags. SSH algorithm selections are read from DSM's `in_use` capabilities, rather than inferred from previously requested values. Omitted selections and nondefault ports survive flag changes. Coupled setters receive their freshly observed flags and port under the client's mutation lock. Network DNS fields are treated as one policy: a hostname-only change does not rewrite DHCP-derived DNS; a DNS-policy change retains omitted DNS values from a fresh read. Interface addresses, DHCP leases and default routes remain separate from general hostname/DNS policy.

Proxy passwords use write-only input and an increasing generation. The adapter preserves omitted passwords, checkpoints an acknowledged generation before readback, and retains a reconciliation guard after an unacknowledged secret write. Destroy cannot silently discard a nonzero credential baseline. Exactly-once execution across a lost Terraform RPC response is not promised; inspect DSM after an interrupted apply. The configuration-backup data source observes policy, encryption and backup status without mutations. Recovery-key generation, password rotation, account binding, backup execution and restore remain outside it: these require recovery material and cannot be treated as ordinary stateless flag changes. The vendor setter can return `prikey_session_id` and its UI downloads recovery material. Preserving `enc_method` and omitting `pwd` does not establish that no key is generated, so no setter is exposed.


QuickConnect owns its main policy, relay switch and complete service map as one typed configuration. Automatic router port-forwarding remains an explicit separate policy. Account enrollment, certificate issuance and external connection success are not inferred from configuration readback. Partial policy writes retain an operator-reconciliation guard; no cross-API rollback is promised.

Firewall owns the selected existing profile, its ordered adapter policy and activation intent. It refuses stateless Create, lossy reads, unreviewed profile switches and changes that cannot satisfy conservative declared-management-network admission. Profile storage must read back exactly before activation begins. A saved profile does not complete the operation; only the acknowledged apply task and final settings readback can do that. Earlier partial writes retain an unacknowledged operation baseline. The demonstrated DSM API cannot compare effective kernel rules with stored policy, so out-of-band unapplied edits and kernel-only drift remain a stated limitation. No profile creation/deletion, forced lockout override, background-task stopping or automatic rollback is exposed.


Installed-package policy owns running intent and protected uninstall; Package Center owns automatic-update policy. Version and placement are read completely as observations. Installation, upgrade and relocation are not exposed: the verified quick API does not bind its mutation to an exact selected version, and checking after application migration is too late. Start/stop and uninstall dependency queues must contain only the requested package, and all feasibility failures remain failures. Package operations hold the mutation lock through readback. Targets and acknowledgements survive returned errors in private state; explicit absence can finish an uncertain uninstall without repeating it. A lost RPC response remains outside durable-state guarantees.

DDNS provider catalogue IDs are a set, while configured record IDs must be unique. DDNS configuration and address-update calls are distinct from external DNS propagation, enrollment and certificate issuance. Credentials are write-only generations, and ambiguous create/update outcomes cannot acquire ownership automatically. Deletion intent survives returned errors so a subsequent read can confirm absence without retrying removal. No incarnation UUID is demonstrated for a logically identical provider-slot record.

Physical Ethernet configuration binds `ethN` to its observed MAC through DSM system inventory. General DNS is a separate owner; interface setters retain coupled DNS values from a fresh read. Automatic addresses are observations, not configured static values. MAC changes, unsafe role transitions and post-plan policy changes block writes. A multi-step IPv4/IPv6 operation remains unacknowledged until all requested setter acknowledgements are received; read never completes it based on partial policy storage. Native IPv6 routing/tunnels, HA and NAT transitions require separate workflows. No new address is probed and no TLS or network rollback bypass is introduced.

`MutationReply` accepts DSM's ordinary success acknowledgement with absent/null data while retaining explicit failure/task metadata. `TaskReply` remains strict about task response data and completion semantics. Synchronous mutation helpers reject explicit internal failures and unfinished/task acknowledgements before advancing credential generations. Task-aware controllers still require tracked status and readback.
