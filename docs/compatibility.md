# DSM compatibility

Read and import compatibility have been verified on DSM 7.1.1 using a DS220j. This is not evidence for DSM 7.2 or 7.3, other models, domain accounts, encrypted shares or Btrfs-specific behavior.

Version 0.3.0 was installed through normal Terraform Registry discovery, with its signing key and binary hash verified against the signed release. A reviewed production adoption plan imported twenty-one instances: two shared folders, three users, three groups, two permission policies and eleven service singletons. It contained zero creates, updates, replacements or deletions. The subsequent plan exited 0, imported identities and managed attributes matched the reviewed plan, and SMB remained reachable. Credentials were supplied through ephemeral SOPS values; the DSM password and SNMP secrets were absent from saved plan and state. An encrypted state backup was decrypted and matched the original bytes and JSON. Configuration metadata still enters state and needs protection; a local encrypted copy does not establish off-device backup.

Version 0.4.0 was subsequently installed through normal direct Registry discovery. Terraform verified its registered signing key, the Registry public key matched the reviewed repository key, and the installed binary matched the release archive and signed checksum. Production adoption preserved all twenty-one existing identities and imported seventeen additional instances for a total of thirty-eight managed resources. The reviewed saved plan contained only imports and no creates, updates, replacements or deletions. Every imported managed attribute matched that plan, the subsequent plan exited 0, no reconciliation guard remained, and SMB and verified HTTPS remained reachable before and after adoption. The DSM password was absent from saved plan, state and command logs. State retained mode 0600 on a FileVault-protected device; pre- and post-adoption full-JSON SOPS backups were decrypted and matched the original bytes. Off-device state storage and independent user-data restore remain unconfirmed. This import-only result is not hardware-write evidence.

No hardware mutation, deletion, interruption or data-restore acceptance test has been performed. Those paths are experimental until exercised on a dedicated disposable DSM environment. Fixtures model the observed read shape and researched mutation contracts; they cannot prove hardware writes. Do not use a production NAS as a destructive test environment.

API contract sources include the discovered DSM API catalogue, read-only observations on the stated version, [Synology's File Station API guide](https://global.download.synology.com/download/Document/Software/DeveloperGuide/Package/FileStation/All/enu/Synology_File_Station_API_Guide.pdf), [the DSM adapter at v0.8.1](https://github.com/batonogov/terraform-provider-synology-dsm/tree/v0.8.1/internal/client), and [N4S4's Core User adapter](https://github.com/N4S4/synology-api/blob/969216beecf08b25a1559046efb4c1f37fb8136c/synology_api/core_user.py). DSM Core administration APIs are not covered completely by a public stable specification. API presence alone is not lifecycle support.

## Additional policy coverage

The signed v0.2.0 binary was checked through a private filesystem mirror against twenty isolated imported instances: two shares, three users, three groups, two permission policies and ten service singletons. The final plan exited 0, SMB remained reachable and the DSM password was absent from saved plan and state. This establishes neither normal Registry installation nor production adoption. Upgrade testing from the v0.1.0 isolated sixteen-instance state required only four new imports and zero changes to existing instances.

The development extension also verified complete live readback for terminal access (SSH/Telnet flags), rsync service/account flags, Windows WS-Discovery and per-protocol transfer logging. Each additional resource has synthetic Terraform create/import/update/external-drift/management-only-destroy coverage, including changed configuration on Create and preservation of omitted flags. This does not establish real DSM mutation compatibility.

Shared-folder `hide_unauthorized_files` uses the `hide_unreadable` property requested through the vendor's `advance_setting` addition. Both observed shares returned true. Omitting this new attribute preserves the existing value; it does not change existing shares on upgrade. Explicit configuration owns and drift-detects it. Fixture tests cover explicit drift, omission during another metadata update, and local protection changes without an extra remote write.

These contracts were traced through the DSM 7.1.1 shipped UI sources `webman/modules/AdminCenter/admin_center.js` (SHA-256 `a78318e3afea8644606722eb20f647547d31a85884ef299e1c3b714ae66b1e5e`) and `webman/3rdparty/SMBService/smb-tab.js`. Source inspection was read-only; vendor JavaScript is not executed or redistributed by the provider. The UI explicitly sends individual changed logging/discovery flags, supporting preservation of omitted settings. The original flag-only scope was expanded below. Rsync credentials and custom configuration contents, detailed log filters/retention and log contents remain outside these resources.

The SNMP extension verifies typed readback on the same live DSM with SNMP disabled. The vendor UI establishes the modeled fields, protocol choices, secret omission and character requirements. Active v3 responses and all SNMP mutations are covered only by synthetic fixtures, not live compatibility evidence. Missing inactive protocol settings are represented as null; missing active settings fail. Community values are kept only in memory, and write-only secret versions survive acknowledged-write/readback failures. See the [SNMP guide](guides/snmp.md).

The user-home development extension imported one disabled service into isolated development state with zero remote changes and a subsequent plan exit code of zero. Task discovery returned empty administrative/user groups on the live NAS. Actual task progress, mutations and interrupted-operation recovery remain fixture evidence. The provider requires import before writes, refuses existing home-folder relocation, preserves dependent policies, and never cancels tasks during refresh. See the [user-home guide](guides/user_homes.md).

The expanded terminal read includes port, console-access policy and SSH algorithm selections; rsync includes its SSH port and existing custom-configuration switch. These fields have read-only hardware evidence and synthetic lifecycle coverage, not hardware-write evidence. Automatic configuration-backup mutations are deliberately not exposed because its setter can return new recovery-key material; the response can contain `pwd`, which is ignored and never enters state. DDNS record discovery uses `SYNO.Core.DDNS.Record.list`; `SYNO.Core.DDNS.list` is not a valid substitute on the observed DSM.
